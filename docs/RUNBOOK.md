# Runbook

How helium-backend runs in AWS, how a release happens, and what to do when something goes wrong. For local development see the [README](../README.md); for the infrastructure code see [deploy/README.md](../deploy/README.md).

## What runs where

Region `ap-south-1`. Each environment (`staging`, `production`) has the same stacks, named `helium-<env>-<stack>`.

| Thing | Where | Notes |
| --- | --- | --- |
| API | ECS Fargate service `helium-<env>-api`, private subnets | Behind the internal load balancer `helium-<env>-api`; only HeliumAdmin's security group may call it. Health: `/health/ready` |
| Worker | ECS Fargate service `helium-<env>-worker` | Runs every consumer (`WORKER_QUEUES=*`). Health: `/health/live` on port 3001 |
| Migrations | ECS task `helium-<env>-migrate` | Run once per release, before the services change |
| Image | ECR `helium-<env>-backend` | Tags are commit SHAs and can't be overwritten |
| MongoDB | The existing DocumentDB cluster | User `helium-backend`: read on `helium`, read-write on `helium_messaging` |
| Redis | ElastiCache for Valkey `helium-<env>-valkey` | Primary and replica, TLS, auth token |
| Queues | SQS `helium-<env>-<name>` and `-dlq` | Listed in `deploy/config/queues.ts` |
| Schedules | EventBridge Scheduler group `helium-<env>` | From `deploy/schedules.json` |
| Logs | CloudWatch `/helium/<env>/api`, `/worker`, `/migrate` | JSON lines; search by `requestId` or `correlationId` |
| Alarms | SNS topic `helium-<env>-alarms` | Queue age and DLQ depth per queue; API without healthy tasks |
| Secrets | Secrets Manager `helium/<env>/...` | See below |

## Secrets

| Secret | Holds | Set by |
| --- | --- | --- |
| `helium/<env>/auth-caller-secrets` | `{"helium-admin":"<secret>"}`: each caller and the secret it signs tokens with | Generated by the foundation stack; HeliumAdmin reads its key from here |
| `helium/<env>/mongo-main-uri` | `mongodb://helium-backend:<password>@<cluster-endpoint>:27017/helium?tls=true&replicaSet=rs0&readPreference=secondaryPreferred&retryWrites=false` | You, after running the users script |
| `helium/<env>/mongo-messaging-uri` | The same with `/helium_messaging` | You |
| `helium/<env>/redis-auth-token` | The ElastiCache auth token | Generated by the data stack |

## First-time setup of an environment

1. Fill in `TODO(aws)` in `deploy/config/environments.ts`, then `pnpm cdk synth` (no placeholder warning for this environment).
2. With administrator credentials for the account:
   ```bash
   pnpm cdk bootstrap aws://<account>/ap-south-1
   pnpm cdk deploy helium-<env>-foundation helium-<env>-pipeline helium-<env>-data
   ```
3. Create the database user, from a machine that can reach DocumentDB:
   `BACKEND_PASSWORD='<strong password>' mongosh "<admin URI>" --file deploy/scripts/create-messaging-db-users.js`
4. Put the two MongoDB connection strings in Secrets Manager (table above).
5. In GitHub → Settings → Environments, create `staging` and `production`. Give each an `AWS_DEPLOY_ROLE_ARN` variable (the pipeline stack's `DeployRoleArn` output), and give `production` required reviewers.
6. Set the repository variable `DEPLOY_ENABLED=true`. The next merge to `main` releases.

## Releasing

Automatic: every merge to `main` runs the `deploy` workflow:

1. **Build** the image once, tagged with the commit SHA.
2. **Staging:** push the image to staging's ECR, then `deploy/scripts/release.sh staging <sha>`:
   1. base stacks (`foundation`, `data`), usually unchanged;
   2. the migration task on the new image, run and awaited. **A failed migration stops the release before any service changes**;
   3. the services on the new image. ECS starts new tasks, waits for them to pass health checks, then stops the old ones.
3. **Production:** waits for an approval in GitHub, then the same steps.

Rules that keep releases safe:

- **Code must work with the database before and after its migrations.** Old tasks keep running while migrations apply and while new tasks start. Removing a field takes two releases: stop using it, then remove it.
- Migrations are forward only. Never edit one that has run.
- A release can be repeated: pushing an existing tag is skipped, migrations already applied are skipped, and an unchanged stack is a no-op.

By hand (with the deploy role's credentials): `deploy/scripts/release.sh staging <sha>`.

## Rolling back

- **Automatic:** if the new tasks don't become healthy, the ECS deployment circuit breaker rolls the service back to the previous task definition. The `deploy` workflow fails; nothing else to do but fix the code.
- **By hand**, when a bad release is healthy but wrong: GitHub → Actions → deploy → Run workflow, with `image_tag` set to the last good commit SHA. It skips the build and releases that image to staging, then (after approval) production.
- **Migrations aren't rolled back.** Because code must work with both the old and the new database, the previous image runs fine on the migrated database. If a migration itself damaged data, write a new migration that repairs it.
- Rehearse a rollback in staging after the first deploys, and after any change to `deploy/scripts/release.sh`.

## Rotating secrets

| Secret | How, without downtime |
| --- | --- |
| A caller's token secret | Add a second caller name to `auth-caller-secrets` (`{"helium-admin":"old","helium-admin-2027":"new"}`), redeploy the services, switch HeliumAdmin to sign with the new name and secret, then remove the old entry and redeploy |
| MongoDB password | Run the users script with `BACKEND_USER=helium-backend-2` and a new password; point both URI secrets at the new user; redeploy the services (rerun the last release); then drop the old user (`db.getSiblingDB('admin').dropUser('helium-backend')`) |
| Redis auth token | `aws elasticache modify-replication-group --replication-group-id helium-<env>-valkey --auth-token <new> --auth-token-update-strategy ROTATE --apply-immediately`; update `redis-auth-token`; redeploy the services; then the same command with `--auth-token-update-strategy SET` |

Redeploying after a secret change: rerun the last successful `deploy` workflow run. Tasks read secrets only when they start.

## When an alarm fires

| Alarm | Meaning | First steps |
| --- | --- | --- |
| `<queue>-oldest-message` | Messages wait too long | Is the worker running and healthy (ECS console, `/worker` logs)? Are handlers failing and retrying? Scale the worker out if it's just load |
| `<queue>-dlq` | Messages were parked or ran out of retries | Read a few (SQS console → the `-dlq` queue → poll); each has `parkReason` if parked. Fix the cause, then move them back: `aws sqs start-message-move-task --source-arn <dlq arn>` |
| `api-no-healthy-targets` | The API's readiness fails, or its tasks are down | ECS console (are tasks running?), then the `/api` logs: a failed readiness check is logged with the dependency that is down (MongoDB or Redis) |

Alarms go to the SNS topic `helium-<env>-alarms`: by email for now, to Slack once AWS Chatbot is connected to the team channel.

## Messaging

The operations routes need the `messaging:ops` permission (the `admin` role). Everything below works locally too, against mock-meta.

| Situation | What to do |
| --- | --- |
| **Stop all sending now** | `PUT /internal/v1/ops/messaging/kill-switch {"on": true}`. Within a second no message is sent; queued ones wait. Undo with `{"on": false}`. Fallback without the API: `SET cfg:wa-pause:{global} 1` in Redis |
| **See what's happening** | `GET /internal/v1/ops/messaging`: queue and DLQ depths, the kill switch, the account (paused? why?), marketing paused (quality), the number's current rate and any pause, sends whose result is unknown, active campaigns |
| **A DLQ has messages** | Read a few in the SQS console (parked messages carry `parkReason`), search the logs by their `messageId`, fix the cause, then `POST /internal/v1/ops/queues/<queue>/redrive` (up to 1,000 per call) and watch the DLQ drain |
| **Account paused** (token expired, restricted) | Fix the cause (rotate `WA_ACCESS_TOKEN`, or resolve the restriction with Meta), then `POST /internal/v1/ops/accounts/main/resume`. Paused campaigns stay paused: resume each |
| **Template paused or rejected by Meta** | Campaigns using it are paused with the reason. Fix or replace the template in WhatsApp Manager, sync (`POST /internal/v1/templates/sync`), then resume the campaigns |
| **Marketing paused** (phone quality flagged) | Lifted automatically when Meta reports the quality restored. Meanwhile review recent campaigns' opt-out and block rates |
| **Redis lost its data** (failover, flush) | Counters and ranks are rebuilt from the database: `POST /internal/v1/ops/campaigns/<id>/reconcile` for each sending or recently finished campaign. Sending campaigns are re-activated; claims prevent duplicates for anything already sent. The suppression mirror is reloaded every 10 minutes |
| **A campaign looks stuck** | `GET /internal/v1/campaigns/<id>/stats`: `waiting` says why the feeder holds it back (send window, daily limit, marketing paused); `inFlight` shows sends without a result. A build with no heartbeat for 5 minutes is re-queued by the sweeper |
| **A send's result is unknown** | Nothing to do: after 15 minutes the settler checks for a status from Meta; without one it sends once more, and fails it (`unconfirmed`) if that is unknown too |

Worker processes run what `WORKER_QUEUES` names: the queues, plus the `campaign-feeder` loop (one leader across all workers). In AWS the worker service runs `*`.

## Useful log searches (CloudWatch Logs Insights)

```text
fields @timestamp, level, msg, requestId, err.message | filter requestId = "<id from an error response>"
fields @timestamp, msg, queue, err.message | filter correlationId = "<id>" | sort @timestamp asc
fields @timestamp, msg, reason, issuer | filter msg = "token rejected"
```
